# 2.0 分支与协作策略

## 推荐方案：单仓库 + 长期 v2 分支

**不新建独立仓库**（除非 2.0 要完全闭源）。理由：

- `pdf_tra` 翻译核心只有一份，修 bug 两边受益
- 1.x 继续维护，2.0 叠加 `miniprogram/` 与云部署
- 文档用 `docs/v2/` 与 1.x 的 `README`、`docs/安装指南.md` 分开

```
main                    ← 1.x 稳定线（本机 Web/CLI），tag v1.x
  │
  └── v2/wechat-miniprogram   ← 2.0 开发线（小程序 + 云）
```

## 分支职责

| 分支 | 用途 | 谁合并谁 |
|------|------|----------|
| `main` | 1.x 发布、本机版修复 | 仅 1.x 相关 commit |
| `v2/wechat-miniprogram` | 小程序、云 API、deploy | 定期 `merge main` 拉核心修复 |

**原则**：

- 改 `pdf_tra/core`、`steps`、`service` 的**通用逻辑** → 先在 `main` 做好，再 merge 进 v2
- 仅 2.0 的代码 → 只提交在 v2 分支（`miniprogram/`、`deploy/`、微信鉴权）

## 版本号

| 线 | 包版本 / Tag | 示例 |
|----|--------------|------|
| 1.x | `pdf_tra.__version__` 0.x | `v0.2.0` |
| 2.0 | 产品 2.0，可与包版本解耦 | tag `v2.0.0-alpha.1` |

小程序 `app.json` 里用 `version` 字段，不必和 Python 包强行一致。

## 目录与 .gitignore

| 路径 | 分支 | 公开仓库 |
|------|------|----------|
| `docs/v2/` | v2 规划，可先在 v2 分支提交 | 建议公开（产品方向） |
| `docs/记忆库.md` 等 | 1.x 内部 | 已 gitignore，仅本地 |
| `miniprogram/` | 仅 v2 | 公开 |
| `config.json` | 两端都不用提交 | 已 ignore |

## 日常流程

```powershell
# 开始 2.0 功能
git checkout v2/wechat-miniprogram

# 1.x 修了翻译 bug 后同步到 2.0
git fetch origin
git merge origin/main

# 2.0 仅小程序改动
git add miniprogram/ docs/v2/
git commit -m "feat(v2): ..."
git push origin v2/wechat-miniprogram
```

## 何时合并回 main？

| 时机 | 操作 |
|------|------|
| M1 内测稳定 | 把 `miniprogram/`、`deploy/` merge 进 `main`，main 同时承载 1.x+2.0 代码 |
| 或长期双轨 | v2 分支一直存在，main 只发 1.x tag |

**建议**：M1 结束前保持 v2 独立分支；上线前再 merge，避免 main 半成品干扰 1.x 用户。

## 备选：独立仓库

仅当 2.0 **闭源商业** 或团队完全拆分时考虑 `pdf-tra-cloud` 新仓，通过 git submodule / pip 依赖 `pdf_tra` 包。当前阶段**不推荐**。
